# CLAUDE.md — AI MIDI Composer

Self-hosted, cross-platform (Windows / macOS / Linux) MIDI composer. A simple web UI lets the user build a song part by part (drums, bass, chords, lead...). Each part is generated by a specialist symbolic-music model (MIDI-GPT) conditioned on tempo, key, chords, genre and the parts already present. Parts can be regenerated, swapped, and sections can be reordered and assembled into an arrangement. Output is standard `.mid` files, ready to drag into any DAW (Logic Pro included).

Use: **personal, non-commercial**. Single user, no accounts.

---

## 1. Hard rules (read first)

1. **One repo, one process.** FastAPI serves both the REST API and the static frontend (`web/`, no build step). The model runs **in-process**. No sidecar, no second server.
2. **Python `>=3.10,<3.13`.** The `midigpt` wheels cover CPython 3.10–3.12 only. Do not raise the upper bound.
3. **Bind to `127.0.0.1` by default.** There is no authentication. LAN exposure only with an explicit `--host 0.0.0.0` flag, which must print a warning.
4. **Never download model weights in tests or at import time.** Weights are fetched on first real generation (Hugging Face cache) or by an explicit `make fetch-models`. Tests that need a model are marked `@pytest.mark.inference` and are skipped by default.
5. **Never commit weights, generated `.mid` files, SQLite databases, or `node_modules`.**
6. **Do not add a dependency without asking.** Propose it with a one-line justification first.
7. **Generation must be reproducible.** Every generation takes a `seed`; the seed is stored with the clip version.
8. **The deterministic post-processor is the source of truth for musical validity.** The model proposes; `postprocess` and `scorer` decide. Never trust raw model output.
9. **Plan before multi-file changes.** For anything touching more than 3 files, state the plan, then implement in small commits.
10. **Code, comments, identifiers, commit messages: English.** UI strings live in one i18n module (default locale `it`).

## 5. Domain model

### 5.1 Time

- Internal resolution: **PPQ = 480**. A 16th-note step = **120 ticks**. A 4/4 bar = **1920 ticks** = 16 steps.
- Note times are stored in ticks **relative to the clip start**. Never store seconds.
- Tempo is stored as BPM (float) on the project; conversions to microseconds-per-quarter happen only in `adapter.py` and `midi_io.py` (`500000 µs = 120 bpm`).
- All bar math goes through `core/timebase.py`. No inline `* 480` anywhere else.

### 5.2 Entities

- **Project**: name, bpm, time signature, key (tonic + mode), genre, `chord_grid`.
- **Track**: project, role (`drums | bass | chords | pad | lead | other`), GM program, name, mute/solo.
- **Clip**: belongs to a track; `bars`; `notes[]` as `{t, p, d, v}` (tick, pitch, duration ticks, velocity 1–127); `locked` flag.
- **ClipVersion**: history of a clip's content with `seed`, `source` (`model | manual | import`), `score`, `params` (JSON), `created_at`. A clip points to its current version.
- **Section**: name, `bars`, `slots{track_id -> clip_id}`.
- **Arrangement**: ordered list of `SectionInstance(section_id)`. The same `Section` can appear several times; editing it changes every instance.
- **chord_grid**: one entry per bar of each section: `{root, quality, pitch_class_set}`.

### 5.3 Operations (must stay simple)

- **Replace a part** = set a slot's clip to another clip, or generate a new `ClipVersion` (the old one stays recoverable).
- **Move a section** = reorder the arrangement list. Context for later generations is recomputed from the new order.
- **Assemble** = duplicate / drag section instances.

## 6. Generation pipeline

### 6.1 Order and context

Default order inside a section: **drums → bass → chords/pad → lead**. Every step gets, as context, all clips already present for that section (and neighbouring sections within the model window). Locked clips are always included as fixed context and never regenerated.

### 6.2 Model integration (`gen/adapter.py`, `gen/engine.py`)

- Load with `InferenceEngine.from_pretrained("prism_medium")`; fall back to `"yellow_medium"` if prism fails to load. Model name is a setting.
- `prism_medium` supports windows of **4, 8, 12, 16 bars** and per-bar attributes (key, pitch range, pitch class set, genre, density, polyphony). `yellow_medium` supports **4, 8** bars and only density / polyphony / note duration (no key, no chords). `config.model_dim` must be a value from the model's `num_bars_map`.
- **Do not hard-code attribute names or value ranges.** Read them at runtime (`GET /info` on the HTTP server, or `engine._analyzer.attribute_sizes()` / `attribute_value_labels()` in-process) and cache them. Map project concepts (density level, chord pitch classes) to the quantized levels the model reports.
- Score conversion (project → midigpt `Score`): resolution 480, tempo in µs per quarter, per-bar time signature, GM `instrument`, `track_type` `melodic` or `drum`.
- Infill uses `TrackPrompt(id, bars=[...])`; from-scratch uses `autoregressive=True`; `ignore=True` omits a track from context; per-bar overrides go in `bar_attributes` / `bar_controls`. Default `InferenceConfig(mask_mode="attention", temperature=1.0, top_p=0.95)`.
- Sections longer than the largest window are generated in windows with 2 bars of overlap; overlapped bars are taken from the earlier window.
- **Spike first (Milestone M1):** inspect the installed `midigpt` classes (`Score`, `Track`, `Bar`, note type) and the attribute list to confirm exact field names before writing the adapter. Do not guess.

### 6.3 Candidates and scoring

For each generation request produce **N candidates** (default 4, setting up to 8) with different seeds, post-process each, score each, keep the best. Store the others in memory for the "Vary" action during the session.

Score (per role weights live in `core/scorer.py`, not scattered):

```
S = 0.4·CT + 0.2·R + 0.2·(1 − min(1, |D − D*| / D*)) + 0.1·(1 − O) + 0.1·K
```

- `CT`: fraction of notes on strong beats (steps 0, 4, 8, 12) whose pitch class is in that bar's chord pitch class set.
- `R`: fraction of notes inside the role's pitch range.
- `D`, `D*`: measured and target notes per bar.
- `O`: fraction of illegal overlaps (same pitch overlapping; any overlap for monophonic roles).
- `K`: bass only — fraction of bass downbeat onsets that coincide with a kick onset (other roles: `K = 1`).
- Drums: replace `CT` with pattern coverage (kick on every quarter in four-on-the-floor styles, backbeat present) and give `CT`'s weight to it.
- A candidate violating a hard constraint (e.g. kick missing on a downbeat for dance genres) is discarded before scoring.

### 6.4 Post-processing (`core/postprocess.py`, deterministic, pure)

Clamp to role range, snap to the 16th grid (triplets only if the project enables them), remove duplicate/overlapping notes, force monophony where the role requires it, trim notes crossing the clip end, normalise velocities to 1–127. Optional humanize (small timing/velocity jitter, off by default, seedable).

### 6.5 Roles (defaults in `core/roles.py`, all overridable)

| Role | MIDI range | Polyphony | Notes |
|---|---|---|---|
| bass | 28–55 | 1 | root on strong beats unless style says otherwise |
| chords | 48–79 | up to 6 | voice-leading: max 7 semitones jump between chords |
| pad | 48–84 | up to 6 | long notes |
| lead | 60–96 | 1 | hook, sparse |
| drums | GM drum map | — | below |

GM drum map: kick 36, snare 38, clap 39, closed hat 42, pedal hat 44, open hat 46, low/mid/high tom 45/47/50, crash 49, ride 51.

### 6.6 Planner (optional, behind an interface)

`Planner.plan(genre, key, bpm, structure) -> {chord_grid, sections, per_bar_controls}`. Implementations: `RuleBasedPlanner` (default, no network, common progressions per mode) and `LLMPlanner` (calls an external LLM API, key read from env, disabled unless configured). The generator never depends on a specific planner.

## 7. REST API (all JSON, prefix `/api`)

```
GET    /health
GET    /models/info                         # active model, bars windows, attribute sizes
GET/POST   /projects            ; GET/PATCH/DELETE /projects/{id}
POST   /projects/{id}/tracks    ; PATCH/DELETE /tracks/{id}
POST   /projects/{id}/sections  ; PATCH/DELETE /sections/{id}
PUT    /projects/{id}/arrangement           # ordered section instance list
GET    /clips/{id}              ; PATCH /clips/{id}          # notes edit, lock
GET    /clips/{id}/versions     ; POST /clips/{id}/restore/{version_id}
POST   /generate                            # {section_id, track_id, bars, controls, n_candidates, seed?}
POST   /generate/vary                       # next-best candidate from the last generation
GET    /export/project/{id}.mid             # master multitrack
GET    /export/track/{id}.mid               # single track over the arrangement
POST   /import/midi                         # import .mid as clips (context or content)
```

`/generate` is long-running (seconds): return a job id and stream progress over Server-Sent Events (`GET /jobs/{id}/events`); the first candidate's notes may be streamed as soon as available. Jobs are serialized through one worker (single model instance); cancelling a job must abort sampling.

## 8. Frontend

Three views only. Keep it simple; resist adding more.

1. **Arrangement**: rows = section instances in order, columns = tracks. Each cell is a clip with `Generate / Vary / Regenerate with note / Lock / Replace`. Drag to reorder sections, duplicate instance, rename.
2. **Clip editor**: minimal piano roll (canvas, pan/zoom, draw/move/resize/delete, snap to 16th) and a drum step grid for drum tracks.
3. **Transport + export**: play section / play all, loop selected section, tempo display, export buttons.

Rules:

- Server state is authoritative; the store mirrors it. No `localStorage` for project data.
- Playback schedules notes with Tone.Transport using ticks → seconds from the project tempo; mute/solo applied client-side.
- Piano roll and timeline must stay at 60 fps for a 64-bar, 6-track project (canvas, no per-note DOM nodes).
- Every user-visible string goes through `web/js/lib/i18n.js`.
- Plain ES modules only: no frameworks, no transpilation, no npm packages. Third-party code is vendored as prebuilt files under `web/vendor/`.
- Generation is always cancellable; show per-cell progress.

## 9. Testing

- `tests/core`: unit + property tests (Hypothesis) for `timebase`, `postprocess` (idempotence, range, no overlaps), `scorer`, `drums`, `harmony`. Golden-file tests for `.mid` export (tempo map, PPQ 480, track names, GM programs).
- `tests/api`: FastAPI TestClient, in-memory SQLite, a `FakeEngine` that returns deterministic notes. Cover replace / reorder / duplicate-section semantics and version restore.
- `tests/inference` (`-m inference`): smoke test per model — generate 4 bars for each role, assert post-processed output is valid and in range. Never assert exact notes.
- Frontend: no JS test runner. Keep frontend logic thin; tick/second conversions mirror `core/timebase.py`, which is the tested reference.
- Bug fixes ship with a regression test.

## 11. Known risks and open items

- **Gated weights.** `Metacreation/MIDI-GPT` on Hugging Face is gated: the licence must be accepted on the Hub and the machine authenticated (`hf auth login` or `HF_TOKEN`) before the first download. Never commit or log the token. See `docs/midigpt-notes.md`.
- **Weights licence.** Code is MIT; the Hugging Face model card lists CC-BY-NC-4.0 for the weights while the paper mentions Open RAIL-M. Personal use is fine. Do not redistribute weights, do not bundle them in installers, do not add any commercial feature without re-checking the licence.
- **Checkpoint maturity.** `prism_medium` and `expressive_medium` were published as work-in-progress checkpoints. Keep `yellow_medium` working as the stable fallback at all times.
- **Attribute and field names** of `midigpt` are verified at runtime (M1), not assumed.
- **No chord conditioning in `yellow_medium`.** When it is the active model, harmony coherence comes only from context tracks and from the scorer's `CT`; use more candidates (N=8).
- **Latency** is unmeasured until M5; do not promise numbers in the UI.
